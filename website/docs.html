Ghostget documentation

Everything you need to search, inspect and install Microsoft Store apps from a terminal — without ever signing in. This page doubles as the project wiki: it covers the same ground as the README and the docs/ folder in the repository, in one browsable place.

New here? Run the three commands below. --dry-run never downloads or launches anything, so it's safe to try immediately.

Quick start

npx ghostget search terminal          # find an app
npx ghostget show 9N0DX20HK701        # price, size, package family
npx ghostget install 9N0DX20HK701     # install it

npx asks once before downloading the package; add --yes to skip that in scripts. You can also pass a name (install "windows terminal") or a Store URL. If a name matches more than one app, ghostget asks which, or fails with the list — it never guesses.

Commands

<app> is a Store product ID (9N0DX20HK701), a Store URL, or a name.

CommandWhat it does
search <query>Search the Microsoft Store. Aliases: s, find
show <app>Details: publisher, price, version, size, package family, installer URL. Alias: info
install <app>Download, verify and launch the Store installer. Aliases: i, add
download <app>Download and verify the installer without running it. Alias: dl
url <app>Print the direct installer URL (stdout only, easy to pipe)
list [filter]List installed Store apps (Windows). Alias: ls
doctorCheck the Windows version, the Store services and the network

Examples

ghostget install "visual studio code" --dry-run      # see what it would do
ghostget install 9N0DX20HK701 --wait                 # wait until it shows up as installed
ghostget url 9N0DX20HK701 | clip                     # copy the installer link
ghostget search python --json | ConvertFrom-Json     # script it
ghostget doctor                                      # why won't it work?

Options

Useful flags across commands. Run ghostget --help for the complete, per-command list.

--dry-run --wait --force --no-verify --dir <path> --market <CC> --locale <tag> --json --exact --limit <1-20> --yes

--wait waits until the app shows up as installed; it works for Store packages, not for apps the Store installs with a vendor's own installer.

How it works

Ghostget does what the Get button on the Microsoft Store website does, from a terminal. It never touches a Microsoft account.

name / id / URL │ ▼ ┌──────────────┐ search storeedgefd.dsx.mp.microsoft.com /v9.0/search (fallback: /manifestSearch) │ resolve │──────────▶ └──────────────┘ details displaycatalog.mp.microsoft.com /v7.0/products (fallback: storeedgefd /products/{id}) │ ▼ ┌──────────────┐ GET get.microsoft.com /installer/download/{id}?cid=website_cta_psi │ download │──────────▶ → a ~800 KB .exe, Content-Disposition names it after the app └──────────────┘ │ MZ header, size == Content-Length, name sanitised ▼ ┌──────────────┐ Get-AuthenticodeSignature: Status = Valid AND signer O = "Microsoft Corporation" │ verify │ otherwise: delete the file, exit 7 └──────────────┘ │ ▼ ┌──────────────┐ Start-Process (so UAC works, like double-clicking it) │ launch │──────────▶ the Store's own installer finishes the job in its window └──────────────┘

The four Microsoft services

ServiceUsed forNotes
get.microsoft.com/installer/download/{id}The installer itselfGET only (HEAD answers 405). Unknown ids answer 404.
storeedgefd.dsx.mp.microsoft.com/v9.0/searchSearchThe API the Store app itself uses.
…/v9.0/manifestSearchSearch fallbackThe API behind winget --source msstore. Doesn't list some apps (e.g. Spotify).
displaycatalog.mp.microsoft.com/v7.0/productsProduct detailsKnows no Win32 (XP…) apps.
storeedgefd.dsx.mp.microsoft.com/v9.0/products/{id}Delivery type, Win32 detailsUsed when the display catalog has nothing.

None of them needs a login. They are undocumented, which is the main risk of this project: Microsoft can change them. The mock server in test/support/mock-store.js and the fixtures in test/fixtures/ are trimmed copies of real responses, so a change shows up as a failing test after the fixtures are refreshed.

Decisions and the evidence behind them

  • A name is never guessed. ghostget proceeds on its own only when there is one result, or exactly one whose name equals what you typed. Otherwise it asks, or fails with candidates and exit code 4.
  • Two catalogs, because each is missing things. manifestSearch returns nothing for "spotify"; the display catalog returns nothing for any XP… id. Each fallback was added after observing that on the live services.
  • Free or paid is decided carefully. Win32 apps report a numeric price of 0 even when paid (localised labels like "Ücretsiz"), so ghostget reads the English words Free/Paid and treats anything else as unknown.
  • Signature check instead of a pinned hash. Installers are generated per product and change, so a fixed hash is impossible. What's stable is who signs it: Valid and organisation exactly Microsoft Corporation.
  • PowerShell for the Windows parts, called with -EncodedCommand and data passed through environment variables — nothing you type is concatenated into PowerShell source.

Delivery types

What ghostget deliberately does not do

  • Sign in, handle credentials, or handle payment.
  • Elevate, or change any Windows setting (doctor prints fix commands but never runs them).
  • Pick between apps for you.
  • Bypass purchases, licences or DRM. The web installer only offers what Microsoft offers any visitor.

Safety model

Nothing ghostget downloads is ever launched unless Microsoft's own Authenticode signature verifies. A single flipped byte is enough to fail the check, and the file is deleted.

  • Three Microsoft hosts, HTTPS only. Endpoint overrides (for tests or mirrors) must be https, or http on localhost.
  • Signature check. Get-AuthenticodeSignature must report Valid and the signer's organisation must be exactly Microsoft Corporation. --no-verify exists, prints a warning, and is not recommended.
  • Sanity checks. The download must be a Windows executable of the announced size. The server-supplied file name is stripped of paths and reserved names.
  • No credentials, no payment. Paid apps are refused unless you pass --force, which only opens Microsoft's own installer, where you decide what happens.
  • No elevation, no settings changes. doctor prints the commands that would fix a problem; it never runs them.
  • No telemetry. The only network traffic is to the three Microsoft hosts.
  • No shell injection. PowerShell is called with fixed scripts; anything you type reaches it through environment variables.

Found a security problem? Do not open a public issue — use GitHub's private Report a vulnerability instead.

Library / API

import { searchStore, getProduct, installApp } from 'ghostget';

ESM only, Node 20.3+, no dependencies. Types ship as generated .d.ts files, built by npm run build:types. From CommonJS on Node 22.12+ you can require('ghostget'); on older Node use await import('ghostget').

Example: install with progress

import { searchStore, getProduct, installApp } from 'ghostget';

const [best] = await searchStore('windows terminal');
const app = await getProduct(best.id);
console.log(app.name, app.price.free, app.version);

const result = await installApp(best.id, {
  wait: true,
  onEvent: (e) => console.log(e.type),
});
console.log(result.status); // 'installed'

PowerShell edition

One dependency-free file that does search, show, install, download and url. Runs in Windows PowerShell 5.1 (already on every Windows 10/11) and PowerShell 7.

& ([scriptblock]::Create((irm https://raw.githubusercontent.com/SkyLostTR/ghostget/v0.2.0/scripts/ghostget.ps1))) install 9N0DX20HK701

Pin the URL to a release tag (as above) and, if you like, read the script first: it is one file and every release lists its SHA-256. Options are PowerShell-style: -DryRun, -NoVerify, -Force, -Dir, -Market, -Locale, -Limit.

Troubleshooting

Start with ghostget doctor. It checks the Windows version, the services the Store install path depends on, and whether the three Microsoft hosts are reachable, and prints the exact command for each fix. It never changes anything itself.

CodeMessage starts withWhat to do
2Unknown command / optionCheck ghostget --help. Some options belong to one command only
3Nothing … matchesUse fewer words, or search with ghostget search
3No … product with id …The id is wrong, or the app isn't sold in your market. Try --market US
4"…" matches N appsRe-run with the Store id from the list
5Could not reach …See Network below
6… needs Windowsinstall/list/signature checks only work on Windows. From WSL, run ghostget from Windows PowerShell
7not signed by Microsoftghostget deleted the file. Retry; if it persists, something on your network is altering downloads
8is a paid appBuy it in the Store, or --force to open the installer and decide there
9Windows cannot deploy Store packages right nowInstallService, ClipSVC or AppXSvc is Disabled. The message names which service(s) and the exact Set-Service fix — run it (PowerShell as Administrator) and retry, or pass --force to launch the installer anyway

The Store installer opens but nothing installs

  1. ghostget install now checks InstallService, ClipSVC and AppXSvc itself before downloading anything, and stops with exit code 9 and the exact fix if one is Disabled (unless the app is Delivery: WPM, or you pass --force). If you still land here, run ghostget doctor — a fail on any of those three means the service is Disabled. Set it back to Manual (PowerShell as Administrator): Set-Service -Name InstallService -StartupType Manual.
  2. If Windows Update (wuauserv) is Disabled, set it to Manual. That does not turn automatic updates back on.
  3. Look at the installer window: it shows the Store's own error code, which you can search for.

Network

  • Behind a proxy: Node ignores HTTPS_PROXY unless you set NODE_USE_ENV_PROXY=1 (Node 24+). The PowerShell edition uses the Windows proxy settings.
  • TLS inspection / corporate CA: set NODE_EXTRA_CA_CERTS=path\to\ca.pem, or use the PowerShell edition.
  • Only one host fails in doctor: that endpoint is down or blocked. Search has a fallback; the installer host does not.

Still stuck? Open an issue and paste the output of ghostget --version, ghostget doctor and the command you ran, with --verbose.

FAQ

Do I have to turn Windows Update on?
ghostget never calls the Windows Update client and never needs an account. But the Store delivers many apps through Windows Update infrastructure. Setting the service (wuauserv) to Manual is the recommended minimum. Keep InstallService, ClipSVC, AppXSvc and BITS out of Disabled too: install checks the first three itself before downloading anything and stops with exit code 9 and the exact fix if one is off (unless the app uses WPM delivery, or you pass --force). ghostget doctor flags a bad setup and prints the one-line fix.
The installer window still asks me to sign in.
Some apps (age-rated content, subscriptions, entitlements) need an account, and that is Microsoft's rule, not something ghostget can or should get around.
It says the app is paid.
The web installer cannot buy anything for you. Buy it in the Store, or use --force to open the installer and decide there.
It cannot reach Microsoft behind a proxy.
Node ignores HTTPS_PROXY unless you set NODE_USE_ENV_PROXY=1 (Node 24+). The PowerShell edition uses the Windows proxy settings.
Is this allowed?
ghostget uses public endpoints and the same installer link the Microsoft Store website hands to every visitor. It does not bypass purchases, licences or DRM. The endpoints are undocumented, so Microsoft may change them — that's the main risk of this project. It is an independent project and is not affiliated with or endorsed by Microsoft. Contributing

Ghostget is small on purpose: zero runtime dependencies, one job, done carefully.

git clone https://github.com/SkyLostTR/ghostget && cd ghostget
npm install
npm run check        # type-check, then run every test
node bin/ghostget.js doctor

Rules that keep it maintainable: no runtime dependencies, types live in JSDoc, library code never prints or exits, data on stdout / everything else on stderr, nothing user-controlled is spliced into PowerShell, and the signature check is never weakened to pass a test.
